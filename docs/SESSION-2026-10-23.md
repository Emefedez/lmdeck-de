## 1. Strata in VS Code Copilot (editor latency)

**Problem.** Strata is fast on the server but editor chat was slow: the first token took over two minutes.

**Cause.** The client, not the model: Copilot sends ~72 tool schemas (19,366 tokens) with every request, and Strata's
default prompt path (decode windows) reads a 19k-token prompt at ~15 tok/s. Measured time to first token was about
166 s at chunk 2048; prompts at 10k tokens took 722 s before the chunked path, 85.7 s at 2048.

**Decision.** Fix the cheapest things first, chat last: chunk size, tool set, system prompt, prompt caching; chat gets
a leaner model/tool profile. The adopted order, with the request sizes behind it, is
[WORKING-PATH-strata-in-editors.md](WORKING-PATH-strata-in-editors.md); the reasoning is
[PLAN-strata-in-editors.md](PLAN-strata-in-editors.md).

**Done here (steps 1-3 of the working path).**

- `strata.prompt_path = "2048"` for editor use (2048 is the balance: 8.4x prompt speedup, 2.55 GB of chunk buffers,
  decode unchanged; 4096 is faster on prompts but leaves ~8.5 GB of arena and has not shown a decode benefit).
- VS Code Fix (inline) and Chat can use different models (`vscode.inline_model`, `vscode.chat_model`; both empty by
  default = whatever `vscode.model` is), so the slow chat case can be given a smaller model while Fix keeps the big
  one. `src/vscode.rs` picks them and the extension applies them.
- A Copilot tool drop list (`server.copilot_drop`, with `server.tool_allow` winning) so the 72 schemas (19,366
  tokens) can be cut to about 4k, which is the change that matters most: ~166 s -> ~35 s on a 20.5k prompt.

**Not done (steps 4-5).** The lean Copilot system prompt needs a captured request first; `strata_prefix` reuse
(pinning a prompt-cache checkpoint between turns) is only planned, lmdeck still sends no `strata_prefix`. Chat
remains the worst case by design: Strata's prompt read is linear in tokens, so the tool payload and prompt have to
shrink, or the turn has to reuse a prefix. See WORKING-PATH-strata-in-editors.md for both.

**Status.** Chunk 2048 is set and measured. Steps 1-3 are in; 4-5 are the remaining editor work.

## 3. Prism ternary GGUFs (PQ2_0 / PTQ1_0)

Full write-up: [TERNARY-PRISM.md](TERNARY-PRISM.md). Short form:

**What it is.** Huihui's `...-Ternary-Bonsai-PQ2_0` uses ggml type 142 (group 128), plus `prism.hadamard.*` metadata:
the weights are stored rotated and a loader must undo the rotation. Stock llama.cpp knows types 0-42 and fails with
`invalid ggml type 142. should be in [0, 43)`.

**Upstream.** Issue #29058 is open. PR #29077 (hadamard for the CPU backend, 16 files, ~+737) was closed unmerged and
measures ~0.4 tok/s here, so it was not ported. PR #29672 is open.

**Fork.** `PrismML-Eng/llama.cpp`, branch `prism`, built at `73bfe6c` (2026-10-19) with Vulkan into
`~/.local/share/lmdeck/llama-prism`. Adds `fwht.comp` (136 lines), PQ2_0/PTQ1_0 dequant and matmul shaders. Ordinary
GGUFs run on it unchanged.

**Measured** (lmdeck's launcher, one stream, greedy):

| Run | Prompt | Decode |
|---|---|---|
| Huihui PQ2_0, 7.2 GB, Prism | 37.3 tok/s on 519 tokens | 6.8 tok/s |
| Q2_K 10.1 GB, Prism | 13.3 tok/s (short prompt) | 4.9 tok/s |
| Q2_K 10.1 GB, stock | 13.5 tok/s (short prompt) | 4.9 tok/s |

Load: Huihui 5.6 s through lmdeck, 130 tensors on Vulkan0, 2 graph splits, coherent answers. The fork costs nothing
measurable on a normal model; the ternary file saves memory (7.2 vs 15.0 GB for 4-bit MLX) but decodes at about half
the speed.

**Implemented ("Auto + badge", approved this session).**

- Header detection: `GgufMeta` stores `file_type`, `max_type` and `prism`; `needs_prism()` is true for
  `prism.hadamard.*` or a highest type above 42 (up to 143). `gguf_unsupported()`/`gguf_unsupported_with()` decide
  the user-facing "cannot load" reason; both scan paths and the `/lmdeck/models` compat block use them.
- Second build: `llama.prism_path` setting + `Config::prism_server()`, `llama_server_for()` and `runs_prism()`.
  Resolution: per-model `engine` -> auto (ternary header + configured Prism build) -> `llama.server_path` / managed
  build -> `$PATH`. A missing configured binary fails the load with its path, not the upstream type error.
- Per-model override: `[overrides."<model>"].engine = "stock" | "prism"`, `POST /lmdeck/override` key `engine`
  (`auto` clears it), TUI **Engine** field in the model settings popup (Enter cycles auto -> stock -> prism, `x`
  clears), an "Engine" line in Details, a cyan `prism` / red `needs Prism build` marker in the Models list, and the
  panel's meta line gets a `prism ·` prefix and a tooltip sentence.
- API: `/lmdeck/models` returns `needs_prism`, `engine` (effective) and `engine_choice` (`auto`/`stock`/`prism`);
  `lmdeck ls` no longer lists a file under "Cannot load:" when a Prism build is configured.
- Config here: `llama.prism_path` = `~/.local/share/lmdeck/llama-prism/bin/llama-server`, `llama.server_path` empty
  (the interim global override is reverted).

**Verified.**

- `cargo test --release`: 85 passed, 3 ignored. New tests: Prism header detection (`needs_prism`), engine routing
  (auto/override/missing build).
- Live daemon: `/lmdeck/models` shows `prism/auto` for the Huihui file and `stock/auto` for MLX, Q2_K and
  `strata/q2_0`; overriding to `stock`, back to `auto`, then `prism` and to `auto` all reflected immediately and
  cleaned the override out of `config.toml`.
- Loads through lmdeck: Huihui loaded in 5.6 s on the Prism binary with the expected flags; Q2_K loaded in 6.8 s on
  the stock binary. Both unloaded afterwards.
- `lmdeck ls` shows no "Cannot load:" section.
